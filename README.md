
# TaskFlow Task-Tracker для руководителей проектов (тим лидов, фрилансеров)

## 1. Назначение системы

Система позволяет делиться ходом работ с заказчиком, скрывая внутреннюю кухню (бэклог, промежуточные задачи, черновики). Заказчик получает ограниченный доступ только к релевантным данным.

---

## 2. Пользователи системы

| Поле | Описание |
| :--- | :--- |
| **ID** | Уникальный идентификатор пользователя |
| **Логин** | Уникальное имя пользователя для входа |
| **Пароль** | Хешированный пароль |
| **Роль** | `OWNER`, `CLIENT` или `TEAM` |
| **Имя** | Отображаемое имя пользователя |
| **Контактные данные** | Email, телефон (  телефон опционально) |
| **Стоимость часа (hourly_rate)** | Ставка в валюте (например, `1500 ₽/час` или `$50/час`). Используется для расчёта стоимости проекта. |

| Тип пользователя | Описание |
| :--- | :--- |
| **User** | Владелец аккаунта. Имеет логин, пароль и роль. |
| **Client** | Заказчик. Привязывается к конкретному проекту. Видит только свои проекты. |
| **Owner** | Фрилансер, создавший проект. Является суперпользователем внутри своего проекта. |
| **Team** | Член команды разработки. Может быть назначен исполнителем или ревьювером задач. |

## 4. Роли и права доступа

| Роль | Доступ к чтению проектов | Создание задач | Назначение людей | Удаление пользователей |
| :--- | :--- | :---: | :---: | :---: |
| **OWNER** (Фрилансер) | Все свои проекты | ✅ Да | ✅ Да | ✅ Да (внутри своей команды) |
| **CLIENT** (Заказчик) | Только проекты, привязанные к заказчику | ❌ Нет | ❌ Нет | ❌ Нет |
| **TEAM** (Разработчик) | Только задачи с активным назначением | ✅ Да (в проекте с активным назначением) | ❌ Нет | ❌ Нет |

### Особенности прав

- **OWNER** — обязателен для существования проекта. Без OWNER'а проект не может быть создан.
- **CLIENT** не видит задачи других заказчиков.
- Для **CLIENT** доступен фильтр по тегам (например, показать все задачи с тегом `question`).

## 5. Задачи (Task)

### 5.1. Атрибуты задачи

| Поле | Тип / связь | Описание |
| :--- | :--- | :--- |
| **id** | `int` (PK) | Идентификатор задачи |
| **tenant_id** | `int` → `Tenant.id` | Арендатор (изоляция данных), индекс |
| **project_id** | `int` → `Project.id` | Проект, к которому относится задача |
| **title** | `str` | Название задачи (обязательно) |
| **description** | `str \| None` | Описание, что нужно сделать |
| **status** | `str` | Статус выполнения (см. п. 5.2) |
| **priority** | `str` | Приоритет: `LOW`, `MEDIUM` (по умолчанию), `HIGH`, `CRITICAL` |
| **tags** | M:M → `GithubLabel` | Метки задачи через ассоциативную таблицу `task_github_label` (например, `question`, `bug`, `feature`) |
| **executors** | 1:M → `Executor` | Исполнители задачи. Роль каждого (`role_in_task`: `DEV` / `QA` / `PM` / `REVIEWER` / …) задаётся на уровне `Executor`, а не отдельным полем задачи |
| **estimated_budget** | `Numeric` | Оценка бюджета задачи (поле нужно только для подгонки исполнителей к задачам) |
| **actual_budget** | `Numeric` | Фактический бюджет задачи (поле нужно только для подгонки исполнителей к задачам) |
| **estimated_hours** | `Numeric` | Оценка трудозатрат (часы) (поле нужно только для подгонки исполнителей к задачам)|
| **actual_hours** | `Numeric` | Фактические трудозатраты (часы) (поле нужно только для подгонки исполнителей к задачам)|
| **note** | `str \| None` | Заметка по задаче |
| **task_images** | связь/коллекция | Прикреплённые изображения |
| **created_by** | `int` → `User.id` | Автор задачи |
| **created_at** | `datetime` | Дата создания |
| **updated_at** | `datetime` | Дата последнего обновления |
| **due_date** | `datetime \| None` | Планируемая дата выполнения |
| **deadline** | `datetime \| None` | Дедлайн задачи |
| **version** | `int` | Оптимистичная блокировка (по умолчанию `1`) |

### 5.1.1. Замечания по полям «Assignee» и «Reviewer»

В модели **нет отдельных полей** `assignee` / `reviewer` на `Task`. Вместо этого используется коллекция `executors` (`1:M → Executor`), где у каждой записи есть:

- `user_id` — исполнитель (аналог прежнего `Assignee`);
- `role_in_task` — роль исполнителя в задаче (`DEV`, `QA`, `PM`, `REVIEWER` и т.п.), т.е. «Reviewer» — это исполнитель с `role_in_task = "REVIEWER"`;
- `is_active` / `removed` — активность и soft-delete;
- `hours` / `planned` / `hourly_rate` — учёт часов и ставки по конкретному исполнителю.

Плюсы такой схемы:
- одна задача может иметь нескольких исполнителей с разными ролями;
- сохраняется история переназначений (`removed`, `remove_reason`, `reassigned_reason`);
- ставка фиксируется на момент назначения (`Executor.hourly_rate`), а не берётся из `User.hourly_rate` «на лету».

### 5.1.2. Теги (`tags`) vs строки

`Task.tags` — это **M:M-связь** с сущностью `GithubLabel` (ассоциативная таблица `task_github_label`), а не простое строковое поле. У метки есть `tenant_id`, `name` (уникально в рамках арендатора — `uq_github_label_tenant_name`) и `created_at`. Связь каскадно чистится при удалении задачи или метки (`ondelete="CASCADE"` с обеих сторон).

Это позволяет:
- переиспользовать одинаковые метки между задачами арендатора;
- фильтровать/группировать задачи по метке через join;
- ограничить набор меток рамками тенанта.

## 6. Проекты (Project)

### 6.1. Атрибуты проекта

| Поле | Тип / связь | Описание |
| :--- | :--- | :--- |
| **id** | `int` (PK) | Идентификатор проекта |
| **tenant_id** | `int` → `Tenant.id` | Арендатор (изоляция данных), индекс `ix_project_tenant_id` |
| **name** | `str(100)` | Название проекта (обязательно) |
| **description** | `str \| None` | Описание проекта |
| **budget_hours** | `Numeric(10, 2) \| None` | Бюджет проекта **в часах** |
| **deadline** | `datetime \| None` | Дедлайн (дата окончания проекта) |
| **tasks** | 1:M → `Task` | Задачи проекта (`back_populates="project"`, `cascade="all, delete-orphan"`) |

### 6.2. Замечания по полям «Заказчик» и «Прогресс-бар»

**Заказчик (Client).** Поле `Project.client_id` ссылается на пользователя с ролью `CLIENT` в том же тенанте. После миграции для существующих проектов нужно явно заполнить это поле, чтобы открыть доступ заказчикам.

**Прогресс-бар.** В БД **не хранится** — это вычисляемое значение. С учётом фактических полей модели его можно рассчитать как:

- **Затраченные часы** — `sum(Task.actual_hours)` по всем задачам проекта, либо `sum(Executor.hours)` по всем исполнителям всех задач проекта (более точный вариант — учитывает часы на уровне исполнителя);
- **Итоговые часы** — `Project.budget_hours`, либо `sum(Task.estimated_hours)`, либо `sum(Executor.planned)` (план по исполнителям).

### 6.2. Расчёт стоимости проекта

| Параметр | Источник | Описание |
| :--- | :--- | :--- |
| **Стоимость часа** | `User.hourly_rate` | Индивидуальная ставка фрилансера (OWNER или TEAM) |
| **Стоимость проекта** | Формула | `Сумма (часы_задачи × hourly_rate_исполнителя)` |

> **Важно:** Стоимость рассчитывается на основе ставки каждого исполнителя, а не единой ставки OWNER'а.

### 6.3. Визуальные индикаторы проектов

| Условие | Индикатор |
| :--- | :--- |
| До дедлайна < 30 дней | Проект подсвечивается **жёлтым** в списках |

## 7. Бизнес-правила

| Правило | Описание |
| :--- | :--- |
| **Прогресс проекта** | Прогресс-бар = (Затраченные часы / Итоговые часы) × 100% |
| **Стоимость проекта** | `Сумма (часы_задачи × hourly_rate_исполнителя)` |
| **Снятие исполнителя с задачи** | Плановые и фактические часы и стоимость сохраняются в итогах. Возврат исполнителя не дублирует его вклад. |
| **Теги** | Множественные. CLIENT может фильтровать по ним. |
| **Кнопка «Неудачная оценка»** | Отмечает задачу, где оценка времени была неверной (для последующего пересчёта бюджета/аналитики) |
| **CLIENT доступ** | Только к статусам `To Do`, `In Progress`, `Review`, `Done`. Бэклог скрыт. |
| **hourly_rate** | Хранится в профиле User. Может быть изменён только самим пользователем или OWNER'ом (для TEAM). |
